# Repositories

- Repositories are the **only** layer that touches `AppDbContext`/EF Core. No business logic.
- Generic `IRepositorio<T>` (open generic in DI) gives CRUD; specific repositories (`IClienteRepositorio`, `IActivoRepositorio`, `IHistorialActivoRepositorio`, `ITicketRepositorio`, `ITecnicoRepositorio`) layer on domain-specific queries (uniqueness checks, `Include`-based joins, pagination).
- Write methods (`Agregar`/`Actualizar`/`Eliminar`) **do not call `SaveChanges`** — they only stage changes on the shared, `Scoped` `AppDbContext`. Callers (Services) explicitly call `GuardarCambiosAsync()` to persist. This is deliberate, not an oversight: it's what makes explicit transaction handling (`IUnitOfWork` / `UnitOfWork`, which wraps `IDbContextTransaction`) actually necessary rather than cosmetic — see `../Services/CLAUDE.md`.
- `IUnitOfWork` exists so Services never see EF types. Don't leak `IDbContextTransaction`, `IQueryable`, or `DbSet` out of this folder.
- Paginated queries return `(Items, Total)` and do `Skip`/`Take` over an explicit order: `IClienteRepositorio.ObtenerPaginadoAsync` / `IActivoRepositorio.ObtenerPaginadoConClienteAsync` order by `Nombre`; `ITicketRepositorio.ObtenerPaginadoConJoinsAsync` filters by `Estado` and orders by `FechaCreacion DESC`. Each order is backed by an index (`../Data/CLAUDE.md`) — adding a new sort/filter column means adding its index too.
- **Every paginated `OrderBy` ends with a unique tie-break (`ThenBy(x => x.Id)`)**. `Nombre` and `FechaCreacion` aren't unique (the load data has ~23 tickets per `FechaCreacion` value), and `Skip`/`Take` over a non-deterministic order makes "Cargar más" repeat or skip rows between pages. No extra index is needed: `Id` is the clustered PK, which SQL Server already appends to every nonclustered index key, so `(Estado, FechaCreacion)` still serves `ORDER BY FechaCreacion DESC, Id DESC`.
- `TicketRepositorio` triple-`Include`s Cliente/Activo/Tecnico so `TicketResponseDto` carries resolved names, not raw FK ids — this satisfies the spec's "reporte con JOINs" requirement directly (no separate report endpoint; it would be redundant). It also does `.Include(t => t.Cliente).ThenInclude(c => c.Contratos)` for the SLA calculation.
- `IReporteRepositorio` is the one repository that doesn't wrap a single entity — it queries `AppDbContext` directly since it necessarily crosses Cliente/Activo/Ticket/Contrato, but it's still the only layer touching EF Core, consistent with the rest of the architecture. Aggregations (`GROUP BY`/`SUM`/`AVG`) must run in SQL, never materialized and grouped in C#.
